# 检出图元会触发关联图元组

## R — 原文 (Reading)

> "请注意，当检出某个图元时，Revit 可能检出必要的其他图元，以使请求的图元可编辑。例如，如果图元是在某个组中，则 Revit 将检出整个组。"
>
> — 宦国胜，第5章 5.13.2 图元所有权 约p399

---

## I — 方法论骨架 (Interpretation)

检出不是"你点名要什么就只有什么"，而是一个**传递性扩大**的操作。

- 机制：Revit 的原则是"保证请求的图元可编辑"。若目标图元的可编辑性依赖其他图元（最典型：组内图元——改组成员必须整组一致），Revit 会把必要的关联图元一并检出。
- 推论：
  1. **实际检出范围 ≥ 请求范围**。点一个组里的窗，整组（含组内所有其他图元）被检出。
  2. UI 反馈要按实际范围做：告诉用户"检出的是整个组/这些关联图元"，而不是谎报"只检出了一扇窗"。
  3. 所有权/放弃逻辑同理：RelinquishOwnership 时按实际持有范围考虑。
  4. 批量检出前预估影响：请求集合若含多个组成员，检出集合可能膨胀，要向用户解释。
- 类比常识陷阱：Git/SVN 不会因为你 checkout 文件 A 就自动 checkout 文件 B——Revit 的组检出传播是 BIM 协作特有的"一致性优先"设计。

---

## A1 — 书中的应用 (Past Application)

### 案例 1: 检出组内的窗

- **问题**: 用户选中一个属于组的窗，插件调用 CheckoutElements 检出它。
- **方法论的使用**: 按 5.13.2 的传递性规则——Revit 为使该窗可编辑，检出整个组。
- **结论**: 不能假设只检出了请求的图元。
- **结果**: 插件的 UI 反馈改为展示实际检出范围（整组），用户不再困惑"为什么同事说他的图元被锁了"。

### 案例 2: 团队冲突排查

- **问题**: 用户 A 只改了一扇窗，用户 B 却发现多个图元变成"被 A 检出"。
- **方法论的使用**: 该窗在组中 → A 的检出连带整组，组成员全部归 A 所有。
- **结论**: 检出传播是"组内编辑一致性"在工作共享层的投影。
- **结果**: 排查结论明确，团队约定组相关操作前先沟通。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 编写检出功能的 UI/日志，需要展示或核对实际检出范围。
2. 排查"我没动这个图元，为什么被我锁住了"类团队冲突。
3. 评估批量检出的影响面（是否波及大量组）。

### 语言信号 (用户的话里出现这些就应激活)

- "检出 整个组 / 为什么多检出了"（checkout entire group / extra elements checked out）
- "组内图元 编辑 所有权"（group element ownership）
- "别人说我锁了他的图元"

### 与相邻 skill 的区分

- 与 `revit-nested-link-unload`：同属"传递性影响"家族：前者是组成员随组连带检出（所有权层），后者是嵌套链接随父链接卸载（加载层）——机制相似但作用域对立。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **检出前识别关联结构**
   - 检查目标图元是否属于组（`Element.GroupId`）或其他会产生传播的结构。
   - 完成标准: 请求集合标注了"可能传播"的风险项。

2. **检出后核对实际范围**
   - 用 `WorksharingUtils.GetCheckoutStatus`（或所有权查询）比对实际检出与请求集合。
   - 完成标准: 实际范围被记录并用于后续所有反馈/放弃逻辑。

3. **按实际范围做用户反馈**
   - 完成标准: UI/日志展示实际检出范围，含传播说明（"该图元位于组中，已检出整组"）。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 非组、无依赖的普通图元——检出范围通常就是请求本身（但仍建议核对，机制是"可能"而非"只有组"）。
- 只读操作——不涉及检出。

### 作者在书中警告的失败模式

- 假设检出范围 = 请求范围 → UI 谎报、团队冲突误判（本单元本体）。

### 作者的盲点 / 时代局限

- 书基于 Revit 2014；除组外还有其他传播源（如部分约束、连接关系），书中以组为例点到为止，未穷尽——需在实际项目中用所有权查询验证。

### 容易混淆的邻近方法论

- 嵌套链接的传递性依赖（卸载须通过父链接）：同属"传递性影响"家族，但作用于链接加载而非所有权。
